# AGENTS.md

Internet Expedition **SaaS backend**: a single Django app that ingests saved web
content (text, images, video, audio, screenshots), processes it with **Gemini**,
and stores the generated context + embeddings for later search.

## What exists here, and what doesn't
- Tree = `bookmark/` (Django project: settings, urls) + `core/` (models, API, Gemini provider, embedding builder, media storage, search, tests, migrations).
- **There is no frontend in this tree.** The v1 web UI, browser extension, docker files, and install scripts were removed from this branch.
- **v1 is the `main` branch** — the remote default — and the local `v1-reference` branch points at the same commit. A fresh clone of this repo lands on v1, not the SaaS code.
- v1 files (`capture/`, `process/`, `evaluate/`, `retrieve/`, `extension/`, ...) **do not exist in this tree** — don't assume they do, don't resurrect them. To read v1: `git show v1-reference:process/pipeline.py`.
- **`README.md` and `assets/` are stale v1 docs** (docker setup, browser extension, port 8081, "nothing leaves your computer"). Trust the code, not the README.
- No CI, Dockerfile, or deploy config in the tree.

## Running it
- Python 3.11 venv at `venv/` (built from `requirements.txt`); run everything as `venv/bin/python`.
- `.env` (gitignored) is required: `GEMINI_API_KEY` has **no default** — settings crash without it. `SUPABASE_URL` + `SUPABASE_SERVICE_KEY` (see Media storage) are *optional* — unset = local-disk fallback, everything still works. DB settings default to `postgres`/`postgres` @ `localhost:5432`, database `bookmark`; the `.env` in this checkout points at a Supabase project via `DB_*` vars. Settings read real environment vars *first* (`read_env(overwrite=False)`), so `DB_HOST=… venv/bin/python manage.py test core` overrides `.env` without editing it.
- **Tests need a running Postgres with pgvector** (migration `0001` runs `CREATE EXTENSION vector`; needs a privileged user — Supabase works out of the box):
  `venv/bin/python manage.py test core`
  All tests are offline (Gemini is mocked) but still need the DB. Against a **remote** DB (e.g. Supabase) the full suite takes ~90s — every ORM query is a network round-trip; a local Postgres runs it in seconds. Don't kill a slow run.
- `manage.py runserver` listens on `$PORT` (default 8080 — `manage.py` patches the default).
- `requirements.txt` still carries v1's local-ML deps (`faster-whisper`, `ollama`, `transformers`, `opencv`, ...). The SaaS code only imports `google-genai`, `pgvector`, `langchain-text-splitters`, `requests`, `supabase` (pinned), and the DRF/allauth stack.

## API contract — easy to get wrong
- The URL slot is **dual-purpose**: `POST /capture-context/<capture_id>/` and `POST /capture-embedding/<capture_id>/` take the **Capture** id in the URL (request body ignored). GET/PATCH/DELETE on the same slot use the context's / row's own id, or the `?capture_id=` query form. Wired via a custom `ContextRouter` in `core/api/urls.py` — read it before touching routing.
- Pipeline order: `POST /captures/` → `POST /capture-context/<id>/` (Gemini) → `POST /capture-embedding/<id>/` (400 if no context exists). `PATCH /capture-context/` = reprocess. All context fields are read-only.
- `POST /captures/` is a **superset of the historical JSON contract**: JSON clients send `media.*` items as `{"url": ...}` exactly as before (the worker later downloads them into the bucket in the `processing_media` phase). An extension that collected the files itself can instead send the request as **multipart**: the same `media`/`text`/`image` fields as form values (the JSON object as a string) plus file parts named `file:<kind>:<index>` (index = position in the `media.<kind>` list) — items with a paired file part are stored *at creation time*, in the web process. Size gates (`MEDIA_MAX_FILE_BYTES` per file, `MEDIA_MAX_TOTAL_PER_CAPTURE` total) → 400 with nothing persisted. The response shape is unchanged (source lists still stripped).
- Client-visible statuses: `queued`, `pending`, **`processing_media`** (new), `processing_context`, `processing_embeddings`, `ready`, `failed`. The in-flight cap and the recovery sweep count `processing_media` like the other processing states.
- The 1536-dim `embedding` vector is never serialized to clients (metadata only).
- Auth is JWT-only (dj_rest_auth + simplejwt); every core endpoint requires `IsAuthenticated`; email verification is `mandatory` (in tests it lands in Django's mail outbox).

## Search — `GET /search/` (in `core/search.py` + `SearchViewSet`)
- A GET-only `GenericViewSet` registered on the **plain** `router` in `core/api/urls.py` (the ContextRouter is only for the dual-purpose POST trick). Read-only: no DB rows are written.
- `?q=` (text to search for) is required — missing/blank → 400. `?k=` (max captures, positive int) and `?min_score=` (finite float, floor on the capture's best-chunk score) are optional and **off by default: every capture is returned** — intentional, so callers can evaluate the score distribution before picking a threshold. Don't add default limits.
- `k`/`min_score` apply at **capture** level only (ranked by best-chunk score); a capture that enters carries *all* of its chunks, each with its own score, best-first.
- Heavy lifting lives in the plain function `core/search.py::search_captures(user, query, k, min_score, provider)` — DRF-free by the same convention as `embedding_builder.py`: one paced provider call embeds the query (~4.5s minimum) → pgvector cosine computed **in Postgres** (vectors are never fetched into Python) → rows grouped by capture → metadata joined from `captures` + `capture_context`.
- Result fields per capture: `capture_id`, `rank`, `score` (cosine similarity — higher = better, *not* a percentage), `summary_text`, `created_at`, `chunks[]` (`source_key`, per-chunk `score`, `text` preview truncated to 200 chars by `PREVIEW_CHARS`). The vector never appears in the response; full chunk text is retrievable via `GET /capture-embedding/`.
- The query filters rows by `vector_dims(embedding) == len(query_vector)` **before** annotating `CosineDistance`: pgvector errors on mixed dimensions, and legacy 3072-dim rows (pre-1536 switch) must be skipped, not crash the search. The `vector_dims` `Func` needs an explicit `output_field=IntegerField()` — without it Django inherits the `VectorField` type and tries to prepare the int as a vector.
- The ranking is a full result set with no `LIMIT` → sequential scan (pgvector HNSW index scans require `ORDER BY ... LIMIT`). Fine at personal scale. The 1536-dim request (under the 2000-dim HNSW cap) deliberately keeps an index *possible* for a future LIMIT-based query variant.

## Gemini provider (`core/api/gemini.py`) — don't "fix" blindly
- The only LLMs used: `gemini-3.5-flash-lite` (text/image/video/audio) and `gemini-embedding-2`, requested at `EMBED_DIMENSIONS` (1536, via Matryoshka `output_dimensionality`; the model supports 768/1536/3072). `EMBED_DIMENSIONS` is the single source of truth: `embedding_builder` enforces it at write time, search matches stored rows against it.
- The 4.5s pacing between calls + 429 retry is **intentional** free-tier quota protection (15 req/min per project) — an N-source capture takes ≈4.5s·N, and every search pays one call.
- The 8192-token embedding window: character pre-split → `count_tokens` validation → re-split until it fits (`generate_embeddings`).

## Media storage (`core/storage.py`) — captures own their bytes
- Captured media (screenshot, images, videos, audios) is stored in a storage backend so captures are immune to dead source links. Two backends, one interface, selected by `STORAGES` in settings: **Supabase Storage** when `SUPABASE_URL` is set (writes with the service key — server-side only; reads via public URLs in the dev phase, signed URLs once `MEDIA_PUBLIC=False`), and **local disk under `MEDIA_ROOT`** when it isn't (this checkout, a bare dev machine, and the whole offline test suite — the `supabase` package is never contacted).
- **Object layout is one prefix per capture**: `<capture_id>/screenshot.<ext>` and `<capture_id>/{images,videos,audios}/<source_id>.<ext>`. Deterministic → idempotent (re-uploads replace); scoped → deleting a capture deletes one prefix (`Capture.delete()` does this best-effort; storage errors are logged, never fail the DB delete).
- **The `*_sources` JSON convention**: `url` is a *fetchable reference* — either a bucket object path (stored in our storage) or the original external URL (link-based); `original_url` records what the client reported. Ingest treats an entry as unassessed only while it has an external `url` and **no `original_url`** — that key is the idempotency marker, so re-runs never re-download stored media.
- **Ingest** (`ingest_capture_media` — plain function, no DRF, per the convention): the worker's `processing_media` phase pulls still-external sources in. Sources over `MEDIA_MAX_FILE_BYTES` (default 50 MB — the free plan's per-file cap) stay link-based, *not* a failure. Download failures are collected across **all** sources and raised together as `MediaIngestError` (→ `failed` + `error_note`) *after* the successful rewrites are saved, so a retry re-downloads only what failed.
- **Resolution** (`resolve_source`): a bucket path → full URL (Supabase) or absolute local path (fallback) — exactly what `gemini.GeminiProvider._resolve_file` consumes, so **`gemini.py` is deliberately unchanged**. A *screenshot* missing from storage (a capture predating this change) is skipped with a warning; a *declared media item* whose link died still fails the capture, as before.
- Free-plan economics: 50 MB/file, 1 GB total. `MEDIA_MAX_TOTAL_PER_CAPTURE` (200 MB) gates upload totals; `MEDIA_PUBLIC` / `MEDIA_SIGNED_URL_TTL` / `MEDIA_DOWNLOAD_TIMEOUT` are the env tunables. Flipping the bucket public→private is a one-flag change confined to `SupabaseStorage.url()` — the pipeline only ever asks for a URL.

## Conventions
- `core/embedding_builder.py`, `core/search.py`, and the `core/storage.py` helpers are plain functions by design — no DRF/request objects — so the same code can run from the API viewset, the worker, or a management command (the embedding builder has one: `build_capture_embeddings`; search is viewset-only for now). Builds are idempotent, all-or-nothing (slow API calls happen *before* one transaction); the same is true of media ingest.
- Migration history was **reset** to a single `0001_initial` (commit `d904b82`) after the capture-only model reset; pre-reset migrations exist only in git history / v1 — don't reference or re-add them. It has since grown to `0005`: 0002 non-null user FKs, 0003 worker statuses + `ProviderRateSlot`, 0004 `OneTimeToken`, 0005 per-capture media layout + `processing_media` status. (Stale `.pyc` files in `core/migrations/__pycache__/` are just build artifacts.)
- All Gemini calls are mocked in tests (`FakeProvider` / `MagicMock`). The search *helper* tests run real pgvector cosine math in Postgres using tiny vectors (the column is dimension-unconstrained); the search *API* tests patch `core.api.views.search_captures`. Media tests stay fully offline too: file-backed paths run against the local-disk fallback, the Supabase backend against an in-memory fake (`FakeStorageAPI` / `FakeSupabaseClient`), and downloads against a fake `requests.get`.
- Django 5.2 gotchas the code/tests lean on: `django.core.files.storage.default_storage` is a lazy **object** (never call it); reset its cache by clearing `storages._storages` and setting `_wrapped = empty` (a `None` reset breaks it); `Model.delete()` returns `(count, {label: count})`, and the Collector **wipes the pk on the instance** — read what you need before calling `super().delete()`; an unset FileField reads back as a *falsy* `FieldFile` wrapper, not `None` (truthiness-check, never `is None`).

## Eval test set (in progress — design agreed 2026-10-21, nothing built yet)

The owner wants numbers, not vibes: a **fixed** test set run through the *real* pipeline, with graded queries and recorded results — so pipeline changes (summary prompt, which source types get embedded, chunking) are judged by before/after deltas, not "it works, I guess".

- **Test set** = raw capture fixtures in the real `POST /captures/` payload shape (`text`, `media.images/videos/audios` URL lists, base64 `image` screenshot) — seeded by copying the *raw inputs* of ~8–12 of the owner's real captures (varied: text-only, text+images, video, audio, screenshot) into a **dedicated eval user** (e.g. `eval@…`). Search is per-user, so the eval user's library *is* the pool: fixed across runs → comparable numbers; the real user's data is never touched.
- **Queries**: 3–4 per capture, graded **clear / medium / vague** (owner writes them — only they know what they'd actually ask). Each has a **target** = the chunk where the answer lives, identified by `source_key` (e.g. `text:…:2`, `image:…:0`, `summary:global:0`).
- **Record per query**: target found?, its rank (capture-level + flat chunk rank), where it *actually* came from (source type), top-k hit source types, scores. **Per run**: timestamp, **pipeline version stamp** (label or git sha), dataset size, library size.
- **Cost split**: re-running *search* is cheap — cache query vectors keyed by (user, query, model); a query's vector doesn't depend on the library. *Reprocessing* the captures (real Gemini, paced) is expensive (~15–25 min for 10 captures) and happens only when the pipeline version stamp changes.
- **Analysis = 2D table: query difficulty (clear/medium/vague) × source type (text/image/video/audio/summary)** — `source_key` already carries the source type, so it's free to record. **Trap**: never conclude "drop text chunks" from aggregate hit counts — the summary dominates *vague* queries while raw text chunks are often irreplaceable for *clear/specific* ones. The 2D split is what prevents that wrong call (e.g. a thin summary shows up as vague-query misses → improve the summary → re-run → did the vague row improve?).
- **Surface**: terminal commands only (owner's explicit choice — never an API endpoint). Plain functions in `core/eval/` + management commands, following the `build_capture_embeddings` pattern: seeder (copy raw inputs) → pipeline re-run with version stamp → search runner + recorder → eval command printing the 2D table + run-over-run comparison. New models (`EvalQuery`, `EvalRun` + per-query rows) in the next additive migration (`0006`).
- **Scope**: measures the **retrieval** stage only — the pipeline stops at context; there is no answer-generation step. LLM-as-judge / RAGAS-style metrics (faithfulness, answer relevance, groundedness) apply only if/when an answer step is added, and each judged case costs a paced LLM call. (Metric-family origin: a RAG-evaluation video the owner watched; transcript at `~/Downloads/Rag_evaluation_transcript.txt` — only its retrieval metrics are applicable today.)
